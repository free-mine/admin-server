# OreVein Admin Server

Backend панели владельца Free Mine в Avalanche C-Chain (chainId 43114).
Готовит планы операций, после подтверждения подписывает и последовательно
исполняет транзакции, отдаёт статусы через REST и WebSocket. Поддерживает
OreVein/FreeMine, преемников, Aave, LFJ и Uniswap V3. Капитал и NFT остаются
у OreVein, газ оплачивает кошелёк владельца.

Публичный снимок и постоянный журнал хранятся на основном
[`server`](https://github.com/free-mine/server). Расчёты, проверки и исполнение
операций используют RPC.

API: [Swagger UI](https://free-mine.github.io/admin-server/) и
[OpenAPI](swagger/openapi.yml). Спецификация описывает preview → подтверждение →
исполнение, форматы данных, диапазоны Uniswap, WebSocket и ошибки.

## Запуск

Нужны `RPC_URL` Avalanche C-Chain и `PUBLIC_SERVER_URL` основного сервера.
Оба URL используют HTTP(S). `PUBLIC_SERVER_URL` может содержать префикс пути,
но не логин, пароль, query или fragment; суффикс `/v1` добавляется автоматически.

Задайте переменные в окружении и запустите контейнер:

```sh
docker run --detach --name ore-vein-admin-server \
  --publish 127.0.0.1:3000:3000 \
  --volume ore-vein-data:/app/data \
  --env RPC_URL \
  --env PUBLIC_SERVER_URL \
  --env PUBLIC_SERVER_KEY \
  ghcr.io/free-mine/admin-server
```

API: `http://localhost:3000`. Образ публикуется из `main`; контейнер работает
от пользователя `node` (UID 1000). Порт внутри контейнера — `3000`.
Volume `/app/data` нужен для восстановления незавершённых и ещё не
синхронизированных операций после перезапуска.

Сервер не имеет авторизации и рассчитан на локальный доступ, один экземпляр
на кошелёк. HTTP и WebSocket разрешают браузерный Origin только
`http://localhost` и `https://localhost` на любом порту; `127.0.0.1` и поддомены
в Origin не разрешены. Запросы без Origin разрешены. Для Swagger `Try it out`
раздайте каталог `swagger/` локальным HTTP-сервером и откройте его через `localhost`.

### Ключи и режим чтения

- `PRIVATE_KEY` — ключ текущего владельца OreVein: 64 шестнадцатеричных символа
  с необязательным `0x`. Для исполнения добавьте `--env PRIVATE_KEY` к команде.
- `PUBLIC_SERVER_KEY` — отдельный ключ API для журнала и обновления снимка.
  Создайте его в репозитории `server` командой
  `docker compose exec server node dist/cli/key.js`. Публичное чтение доступно
  без этого ключа. Ключ кошелька остаётся на управляющем; браузер не получает ключи.

Без корректного ключа владельца сервер запускается в read only: доступны
чтение, WebSocket и preview, включая симуляцию от адреса владельца. Исполнение
и восстановление отправки приостановлены, файлы и удалённый журнал не изменяются.
Режим виден в `readOnly` у `/v1/config` и `/ready`; для его смены нужен перезапуск.
При рабочем RPC `/ready` возвращает `200` и в режиме чтения.

### Настройки

| Переменная                 | По умолчанию       | Назначение и диапазон                      |
| -------------------------- | ------------------ | ------------------------------------------ |
| `HOST`                     | `0.0.0.0`          | Адрес прослушивания внутри контейнера.     |
| `LOG_BLOCK_RANGE`          | `10`               | Блоков на запрос событий: 1–10.            |
| `DEPLOYMENT_BLOCK`         | Блок развёртывания | Начальный блок поиска событий, ≥ 0.        |
| `POLL_INTERVAL_MS`         | `3000`             | Опрос транзакций, мс: 100–60000.           |
| `PREVIEW_TTL_SECONDS`      | `120`              | Срок действия плана, с: 30–600.            |
| `RPC_TIMEOUT_MS`           | `20000`            | Таймаут RPC, мс: 1000–120000.              |
| `PUBLIC_SERVER_TIMEOUT_MS` | `5000`             | Таймаут основного сервера, мс: 100–120000. |
| `SYNC_INTERVAL_MS`         | `15000`            | Синхронизация, мс: 1000–600000.            |

Запросы событий `eth_getLogs` охватывают не более 10 блоков, включая обе границы
диапазона. Если `LOG_BLOCK_RANGE` уже задан в окружении, укажите значение от 1 до 10
или удалите переменную, чтобы использовать значение по умолчанию. Значения вне
этого диапазона останавливают запуск с ошибкой `INVALID_ENV_LOG_BLOCK_RANGE`.

## Синхронизация и восстановление

При недоступности основного сервера исполнение через RPC продолжается.
`GET /v1/state` возвращает последний снимок из памяти с `cached: true` и его
возрастом; без снимка — `503`. После подтверждения транзакции сервер запрашивает
обновление, пока снимок не достигнет блока подтверждения.

Изменения журнала записываются в `/app/data/operations.pending.json` до отправки
на основной сервер, подпись — до отправки транзакции. Файл также хранит
синхронизированные незавершённые операции и удаляется, когда всё завершено
и синхронизировано. Потеря volume означает потерю ещё не переданных записей.
Старый `operations.json` автоматически переносится при запуске в режиме записи.

Проверяйте `GET /v1/sync`: готовность RPC в `/ready` не означает, что история
синхронизирована. Ошибка локальной записи или конфликт удалённой ревизии
останавливает исполнение. При `JOURNAL_CONFLICT` сопоставьте локальные и удалённые
записи, устраните причину и перезапустите сервер. Для подтверждённой внешней
замены транзакции используйте `POST /v1/operations/{id}/resolve`.
Preview до подтверждения хранится только в памяти.

## Разработка

Node.js 24 (от 24.13.1). После `npm ci`:

```sh
npm run lint
npm run format:check
npm run check
npm test
npm run build
```

Эти проверки выполняются в CI для каждого PR. `npm run dev` запускает сервер
с отслеживанием изменений; ему нужны те же переменные окружения.
